Interview evidence cards

Twenty original prompts for a ten-minute written practice session. Choose a role, answer one question, work through three follow-ups and check the evidence behind your answer. Finish with one revised sentence and a short list of facts to verify.

Practice material, not validated employer interview questions. These cards do not predict hiring decisions or measure interview readiness. Use your own examples honestly; no interview service or account is needed.

A ten-minute written exercise

Use a separate timer and paper or your own private notes. Pick any card below. A work, study, volunteer or personal-project example is fine. If you have no matching experience, clearly label a hypothetical response instead of inventing a history.

  1. 00:00–01:00 · Choose an example. Note your responsibility and who did the other work.
  2. 01:00–04:00 · Write an answer. Use four to six sentences. Separate observations from interpretations; leave a placeholder for forgotten details.
  3. 04:00–07:00 · Take the follow-ups. Spend one minute on each of the three questions.
  4. 07:00–09:00 · Audit the evidence. Apply the card's evidence check. Mark key claims supported, uncertain or missing. These are personal review reminders, not a score.
  5. 09:00–10:00 · Revise and plan. Correct one overstated or vague sentence. Write what to verify next, where to look and when to check.

Synthetic example. A note says, “Training increased adoption.” The only evidence is that four of six invited colleagues attended a session. A more accurate sentence is, “Four colleagues attended; I have not checked whether they completed the setup task.” The next step is to check that milestone. This scenario and its numbers are invented for practice.

Your result is a revised answer and a short evidence-to-check list. Do not include confidential employer or customer records in anything you share.

Software engineer

SE-01 · Diagnosis under uncertainty

Prompt. Describe a slow request you investigated when the first plausible explanation turned out to be wrong.

  1. What observation made the first explanation less likely?
  2. Which boundary did you measure next, and why did that measurement isolate the problem?
  3. What remained uncertain after the fix, and how would you detect a recurrence?

Evidence check. List one request example, the measurement window, and a comparable before/after observation. Separate your diagnosis from the change another person implemented.

Common pitfall. Treating a faster local run as proof that production latency improved.

SE-02 · A compatible data change

Prompt. Walk through a change to stored data that had to coexist with an older version of the application.

  1. Which old reader or writer could have failed during rollout?
  2. How did you decide the order of the schema, application and data changes?
  3. At which point would rollback stop being safe, and what would you do instead?

Evidence check. Sketch the old and new read/write paths and identify one compatibility check you actually ran. Mark any recovery step that was planned but never exercised.

Common pitfall. Saying the change was reversible without considering data written after deployment.

SE-03 · The cost of a dependency

Prompt. Explain a dependency you removed, replaced or deliberately kept because of its maintenance cost.

  1. Which concrete failure or repeated task made the dependency worth reviewing?
  2. What work would the rejected option have moved onto your team?
  3. What evidence would make you revisit the decision six months later?

Evidence check. Name one affected interface, one recurring cost, and the source of that cost estimate. Distinguish measured effort from a forecast.

Common pitfall. Calling a dependency bad because it is old without showing a problem it caused.

SE-04 · A challenged assumption

Prompt. Describe a code review where you changed your implementation after another person challenged an assumption.

  1. What was the original assumption and the specific counterexample?
  2. Which behavior did you preserve while changing the implementation?
  3. What check would fail if the original mistake returned?

Evidence check. Reconstruct a small input, expected result and failure condition without sharing proprietary code. Identify your own change and the reviewer's contribution.

Common pitfall. Presenting agreement in the review as evidence that the behavior was tested.

Product manager

PM-01 · Prioritizing with limited evidence

Prompt. Describe a prioritization decision made with only a small amount of customer evidence.

  1. Which users supplied the evidence, and who was missing?
  2. What did you postpone, and what was the cost of waiting?
  3. What small observation would have been enough to reverse the priority?

Evidence check. Write the number and source of observations if known, the decision date and the next check. Label assumptions separately from customer statements.

Common pitfall. Turning a few enthusiastic comments into a claim about the whole market.

PM-02 · A launch readiness decision

Prompt. Walk through a launch you narrowed or delayed because a specific readiness condition was not met.

  1. What exact user task could not be completed reliably?
  2. Who could resolve the issue, and what temporary scope was still usable?
  3. What observation was required to reopen the launch decision?

Evidence check. Write the readiness condition as an observable user action and result. Distinguish a passed internal check from a successful user journey.

Common pitfall. Describing a delay as caution without specifying the failure it prevented.

PM-03 · Conflicting workflow requests

Prompt. Explain how you resolved two stakeholders asking for incompatible changes to the same workflow.

  1. What outcome did each stakeholder want beneath the requested feature?
  2. Which constraint prevented satisfying both requests at once?
  3. What did you communicate to the group whose request was deferred?

Evidence check. Draw the two requested paths, identify the conflicting step and record the decision owner. Separate a stakeholder preference from a verified user need.

Common pitfall. Describing consensus while omitting who accepted the tradeoff.

PM-04 · An unexpected experiment result

Prompt. Describe an experiment whose result did not support the improvement you expected.

  1. What was the decision the experiment was meant to inform?
  2. Which guardrail or data-quality issue could change your reading of the result?
  3. What did you stop, keep or investigate after seeing the evidence?

Evidence check. State the measured outcome, comparison, observation period and uncertainty you actually had. If you cannot recall a number, record the missing source instead of reconstructing it.

Common pitfall. Retelling an inconclusive result as a successful learning milestone without naming the changed decision.

Designer

DE-01 · An essential task blocked

Prompt. Describe a design you revised after finding that someone could not complete an essential task.

  1. Which interaction created the obstacle, and how was it observed?
  2. What changed for keyboard, assistive-technology or other affected users?
  3. What part of the task still needed verification after the revision?

Evidence check. Record the task, access method, observed obstacle and subsequent check. Do not describe a visual inspection alone as an accessibility test.

Common pitfall. Claiming the whole experience is accessible because one component was repaired.

DE-02 · Comments versus behavior

Prompt. Explain a usability session where a participant's comments and behavior pointed in different directions.

  1. What did the participant say, and what did you actually observe?
  2. Which alternative explanation did you consider before changing the design?
  3. What follow-up task would distinguish those explanations?

Evidence check. Write one anonymized behavior note beside a separate paraphrase of the comment. Mark the inference connecting them, rather than presenting it as a participant quote.

Common pitfall. Using a positive opinion to dismiss a visible task failure.

DE-03 · Design within a constraint

Prompt. Describe a design decision constrained by a technical limitation that would not be removed before release.

  1. Which part of the desired behavior was unavailable?
  2. How did you compare the compromises from the user's point of view?
  3. What did the final design make explicit about the limitation?

Evidence check. Identify a user task, the constraint and one rejected compromise. Note which parts you personally designed and which were agreed with engineering.

Common pitfall. Showing polished screens without explaining what the user could actually finish.

DE-04 · A handoff mismatch

Prompt. Walk through an implementation mismatch you discovered after handing off a design.

  1. What behavior differed, beyond spacing or color?
  2. How did you decide whether to change the implementation or the design?
  3. What did you add to the handoff so the same ambiguity was less likely next time?

Evidence check. Describe one state transition with its trigger and expected outcome. Record how you verified the resolved behavior, not just the updated design file.

Common pitfall. Treating a revised specification as proof that the shipped interface changed.

Data analyst

DA-01 · A metric definition

Prompt. Describe a metric whose definition changed the conclusion of an analysis.

  1. What did the numerator, denominator and time window include?
  2. Which records were excluded, and who agreed with that choice?
  3. How did the decision differ under the alternative definition?

Evidence check. Write a small invented row example that is included under one definition and excluded under the other. Label it synthetic and keep real customer records private.

Common pitfall. Reporting a percentage without explaining the population it describes.

DA-02 · Missing observations

Prompt. Explain an analysis where missing records were likely to differ from the records you could observe.

  1. What process caused the missingness, as far as you could establish?
  2. Which conclusion was most sensitive to the missing group?
  3. What range or qualification did you communicate instead of a single confident answer?

Evidence check. Separate known record counts, suspected causes and unsupported assumptions. Describe a sensitivity check you ran, or explicitly mark one you only proposed.

Common pitfall. Calling data representative because the available sample was large.

DA-03 · A pipeline discrepancy

Prompt. Walk through a dashboard change that was caused by a data pipeline issue rather than a business change.

  1. Which comparison first made the displayed change suspicious?
  2. Where did the discrepancy enter the pipeline?
  3. What did you tell dashboard users before the corrected result was available?

Evidence check. Name the affected interval and reconciliation check, using anonymized or synthetic values. Distinguish the repaired pipeline from any historical data still awaiting correction.

Common pitfall. Declaring the incident resolved after a successful refresh without checking the missing period.

DA-04 · Limits of attribution

Prompt. Describe a time you were asked to attribute an outcome to a change that was not randomly assigned.

  1. What else changed at the same time or differed between the groups?
  2. Which comparison could reduce the ambiguity, and what would it still fail to establish?
  3. How did you phrase the conclusion so the decision-maker understood its limit?

Evidence check. List the observed association and at least one plausible alternative explanation separately. Identify the evidence supporting each, without inventing causal certainty.

Common pitfall. Using a before/after chart as proof that one action caused the result.

Customer success

CS-01 · An onboarding obstacle

Prompt. Describe an onboarding plan you changed after a customer failed to complete an important step.

  1. What behavior showed that the step was blocked?
  2. Was the obstacle knowledge, access, ownership or something else, and how did you check?
  3. What smaller milestone did you agree on next?

Evidence check. Record the customer's task, the observed obstacle and the next milestone owner. Separate an attended training session from successful product use.

Common pitfall. Treating a completed meeting as evidence of customer adoption.

CS-02 · An escalation update

Prompt. Walk through an escalation where you had to keep a customer informed before there was a confirmed fix.

  1. Which facts were confirmed, and which were still hypotheses?
  2. What could you promise about the next update without promising a resolution time?
  3. How did you coordinate ownership when the issue crossed teams?

Evidence check. Draft a short anonymized update containing impact, known facts, owner and next update time. Mark any workaround as tested, untested or unsuitable.

Common pitfall. Giving an optimistic fix date that the responsible team has not committed to.

CS-03 · Investigating account risk

Prompt. Explain a customer risk signal that you investigated before deciding whether an account needed intervention.

  1. What behavior triggered the signal, and could it have an ordinary explanation?
  2. Whose perspective was absent from the account history?
  3. What evidence changed the action you took?

Evidence check. List the signal, its time window and the confirming or contradicting observation. Distinguish your risk assessment from the customer's stated intention.

Common pitfall. Treating a health score as proof that a customer plans to leave.

CS-04 · A reusable customer resource

Prompt. Describe a recurring customer question you turned into a reusable support or success resource.

  1. Which variations did the resource cover, and which still needed a person?
  2. How did you check whether a customer could use it without your explanation?
  3. What feedback led you to revise or retire part of it?

Evidence check. Identify one question, the resource's intended user and an observed attempt to use it. If time saved was not measured, describe the behavior change instead.

Common pitfall. Claiming efficiency gains from publishing a document without observing anyone use it.

Choose a repeatable card with Python

Requires Python 3.9 or later, with no third-party packages. Save drill.py and cards.json in the same directory. Open a terminal there:

python drill.py --role software-engineer --seed 17
python drill.py --role customer-success --seed 42
python drill.py --role designer --seed -3 --export my-practice.md
python drill.py --help

On Windows, py -3 can replace python. Role values are software-engineer, product-manager, designer, data-analyst and customer-success.

The same role, integer seed and dataset produce the same worksheet. Different seeds may choose the same card because each role has four. The CLI prints the schedule and prompts; it does not run a countdown, collect answers or grade them.

--export PATH additionally saves UTF-8 Markdown to a new file at the explicit path. Relative paths use your terminal's current directory. The parent directory must exist, and existing files are never overwritten. Omit this option to write no file.

For data fields, maintenance and tests, read the README. From the project directory, run:

python -B -m unittest discover -s tests -v

Privacy, limits and related reading

The CLI makes no network requests and never asks for a resume, name or email. It reads the bundled card file and writes only an explicitly requested export. Your terminal may retain output; exported notes are ordinary local files.

This page has no JavaScript, forms, analytics, remote fonts or remote assets. The hosting provider may receive normal page-request logs. Visiting an external link is a separate request to that site.
